# H10 模型轻量化与端侧部署优化 · 实测报告

- 模型参数量：**19,060**
- 输入形状：`[1, 64, 128]`（单通道 log-mel，64×128）
- 测试样本数：16
- 推理设备：CPU（端侧场景）

## 对比结果

| 版本 | 体积 (MB) | 延迟 (ms/批次) | 相对 PyTorch 加速 | 输出最大差异 |
|---|---|---|---|---|
| PyTorch fp32 | 0.080 | 8.382 | 1.00x | — |
| ONNX fp32 | 0.015 | 1.544 | 5.43x | 1.91e-06 |
| ONNX fp16 | 0.051 | 12.450 | 0.67x | 2.23e-03 |
| ONNX int8 | 0.032 | 26.645 | 0.31x | 6.09e-02 |

## 精度保持

- PyTorch vs ONNX fp32 预测一致率：**100.0%**
- PyTorch vs ONNX int8 预测一致率：**100.0%**

## 关键结论（⚠️ 与「量化一定更快」的直觉相反，以实测为准）

1. **最快的是 ONNX fp32**：相对 PyTorch **5.43x**，体积缩到 **19.3%**。
   说明**图优化 + 算子融合本身就是最大收益来源**，不必先上量化。
2. **int8 动态量化在本场景反而更慢**（26.6 ms，相对 PyTorch **0.31x**），
   体积也无优势（fp32 的 **204%**）。根本原因是**模型太小**（仅 19,060 参数）：
   · 动态量化的「运行时反量化」开销 > 权重位宽降低的收益；
   · 小模型的瓶颈是**算子调度/框架开销**，不是权重访存量。
3. **fp16 在本机 CPU 上不提速**（12.4 ms）：多数 x86 CPU 无 fp16 SIMD 加速，
   需转回 fp32 计算反而更慢。fp16 的价值在 **GPU / 支持 fp16 的端侧芯片**。

## 工程取舍（部署优化不能套模板）

| 方案 | 优势 | 局限 | 适用场景 |
|---|---|---|---|
| **ONNX fp32** | 图优化 + 算子融合，实测加速最大 | 体积未压缩 | **小模型首选** |
| ONNX fp16 | 体积可减半 | **CPU 上未必提速** | GPU / 支持 fp16 的端侧芯片 |
| ONNX int8 | 大模型下体积与速度收益明显 | 小模型反而变慢；有量化误差 | **大模型 / 显存受限场景** |

> **正确做法**：先 profile 定位瓶颈（框架开销？权重访存？算力？），再决定优化手段；
> 并做**双重验证**——输出一致性（vs fp32）+ 下游指标（分类/生成质量是否下降）。
